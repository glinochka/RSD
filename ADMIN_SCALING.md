# ADMIN SCALING: Шаблон "ИИ Администратор" для сервисного бизнеса (Beauty / Dental)

## Контекст задачи

Цель: существенно переработать шаблон `crm_admin`, чтобы он работал как полноценный администратор:

- салона красоты / парикмахерской,
- стоматологической клиники,
- и в будущем других схожих ниш.

Ключевые требования:

1. CRM-интеграция должна быть **необязательной**.
2. Нужен **подшаблон** (dropdown): пока `beauty_salon` и `dental_clinic`.
3. Для каждого подшаблона — отдельные настройки (ресурсы, сотрудники, услуги и т.д.).
4. В дашборде — CRUD карточек (мастера/врачи, услуги, кабинеты/кресла, расписание).
5. В дашборде — наглядная загрузка (кто/когда/на какую услугу).
6. Подготовить фундамент под дополнительные удобные фичи.

---

## Что уже реально есть в проекте (по текущему коду)

### 1) Базовая архитектура шаблонного runtime уже есть

- Есть единый `TemplateRuntimeService` в `backend/app/services/template_runtime.py`.
- `message_processor` и `external/chat` уже вызывают единый runtime.
- `function_calling` уже нормализуется в `crm_admin`.

### 2) Для `crm_admin` уже есть контур CRM

- `template_config` для `crm_admin` валидируется в `router_agents/router.py`.
- Реализованы `crm/connect`, `crm/validate`, `crm/health`, `crm/rotate_secret`.
- Есть `CRMToolRegistry` и провайдеры `amocrm`/`bitrix24`.
- В аналитике уже логируются `tool_name/tool_status/latency_ms/crm_provider`.

### 3) В UI уже есть выбор шаблона и CRM-настройки

- На `frontend/src/pages/createAgent.jsx` уже есть выбор `crm_admin`.
- Сейчас CRM-флоу фактически обязательный для сохранения `crm_admin` (валидация подключения + токен/base_url).
- Это конфликтует с новой бизнес-требуемой моделью "CRM optional".

### 4) Дашборд сейчас покрывает общую аналитику, но не операционный admin-учет

- Есть чаты, рассылки, CRM-action analytics.
- Нет предметных сущностей "мастер/врач", "услуга", "кабинет/кресло", "слот записи".
- Нет специализированной визуализации загрузки расписания по ресурсам.

## Целевой продуктовый срез

Шаблон `crm_admin` становится "вертикальным":

- **Подшаблон Beauty Salon**
  - сотрудники: мастера,
  - ресурсы: кресла/рабочие места,
  - каталог услуг,
  - график и записи.

- **Подшаблон Dental Clinic**
  - сотрудники: врачи,
  - ресурсы: кабинеты/установки,
  - каталог услуг,
  - график и записи.

Общий принцип:

- агент может работать как с локальными данными RSD (без CRM), так и через CRM adapter (при подключении),
- UI и API едины, источник данных выбирается через режим исполнения.

---

## Предлагаемая модель конфигурации `template_config` (v2)

Рекомендуемая структура:

- `domain_type`: `beauty_salon | dental_clinic`
- `crm_mode`: `disabled | optional | required`
- `crm_provider`: `amocrm | bitrix24 | null`
- `booking_backend`: `local | crm` (автовыбор по доступности CRM допустим)
- `resources`: доменные лимиты/политики
- `features`: feature flags (например, waitlist, deposits, reminders)
- `ui_preferences`: настройки представления расписания

Пример (beauty):

- `domain_type = beauty_salon`
- `crm_mode = optional`
- `booking_backend = local`
- `resources = { chairs_count, masters_limit }`

Пример (dental):

- `domain_type = dental_clinic`
- `crm_mode = optional`
- `booking_backend = local`
- `resources = { rooms_count, doctors_limit }`

## Поэтапный план реализации

### Этап 0. Контракт шаблона и обратная совместимость

**Цель этапа:** не ломая текущий `crm_admin`, ввести стабильный контракт нового поколения.

Что сделать:

- Зафиксировать `template_config v2` с полями `domain_type`, `crm_mode`, `booking_backend`.
- Добавить мягкую миграцию старых `crm_admin` конфигов:
  - если старый формат, выставлять `domain_type=beauty_salon` по умолчанию,
  - `crm_mode=optional`, если нет явного требования.
- Обновить backend-валидацию `_normalize_template_config` для нового контракта.
- Поддержать чтение старых агентов без обязательного ручного апдейта.

Результат:

- новый функционал запускается без регрессии текущих агентов.

---

### Этап 1. Подшаблоны и доменная схема данных

**Цель этапа:** описать предметные сущности для beauty/dental в БД.

Что сделать:

- Добавить таблицы:
  - `admin_staff` (role: `master|doctor`, специализации, активность),
  - `admin_resources` (type: `chair|room|equipment`),
  - `admin_services` (длительность, цена, привязка к ролям/ресурсам),
  - `admin_schedule_slots` (рабочие слоты сотрудников/ресурсов),
  - `admin_appointments` (записи клиентов).
- Уникальные индексы/ограничения для пересечений по времени (staff/resource conflicts).
- Связать сущности с `agent_id` для многопользовательской изоляции.

Результат:

- появляется нормализованная модель карточек и расписания для дашборда и рантайма.

---

### Этап 2. Unified Booking Service (локально + CRM)

**Цель этапа:** сделать единый доменный слой записи, независимый от источника данных.

Что сделать:

- Ввести `AdminBookingService` (или `AdminDomainService`) с операциями:
  - CRUD сотрудников/ресурсов/услуг,
  - построение доступных слотов,
  - создание/перенос/отмена записи.
- Ввести provider-интерфейс:
  - `LocalBookingProvider` (Postgres-сущности RSD),
  - `CrmBookingProvider` (через CRM adapter, при подключении).
- Выбор провайдера по `template_config.crm_mode` + доступности CRM-connection.

Результат:

- CRM становится опциональной "надстройкой", а не обязательным условием работы шаблона.

---

### Этап 3. API для карточек и расписания в дашборде

**Цель этапа:** дать frontend полный операционный API для управления.

Что сделать:

- Добавить в `router_agents` (или отдельный `router_admin_template`) endpoint-ы:
  - `/admin_template/staff` (list/create/update/delete),
  - `/admin_template/services`,
  - `/admin_template/resources`,
  - `/admin_template/schedule`,
  - `/admin_template/appointments`.
- Добавить endpoint "загрузка/занятость":
  - агрегаты по дню/неделе,
  - матрица занятости `resource x time`.
- Добавить фильтры по `domain_type`, сотруднику, услуге, периоду.

Результат:

- backend готов для полноценного операционного интерфейса администратора.

## MVP-срез (первый релиз)

Рекомендуемый MVP:

1. `crm_admin v2` + `domain_type` (beauty/dental) + `crm_mode=optional`.
2. Локальные сущности: сотрудники, услуги, ресурсы, записи.
3. Базовый CRUD в дашборде.
4. Простой календарь занятости (day/week).
5. Runtime tools: проверка доступности + создание/перенос/отмена записи.
6. Базовые агрегаты загрузки.

## Риски и как снять заранее

1. **Риск: усложнение `template_config` и регрессия старых агентов**
   - Митигировать через совместимость v1/v2 и мягкие default-значения.

2. **Риск: конфликтная логика local-vs-CRM**
   - Митигировать четким provider-контрактом `AdminBookingProvider`.

3. **Риск: коллизии расписания при конкурентных запросах**
   - Митигировать транзакционными проверками и уникальными ограничениями в БД.

4. **Риск: перегруженный UI**
   - Митигировать пошаговым UX: базовые поля в createAgent, расширенный CRUD в отдельном разделе.

## Итого

В проекте уже есть сильный фундамент: единый template runtime, канальный процессинг, CRM adapters и аналитика tool calls.  
Главный следующий шаг — превратить `crm_admin` из "CRM-aware ассистента" в предметный операционный шаблон с подшаблонами, локальным booking-контуром и optional CRM.

Оптимальная последовательность: сначала v2-контракт + доменная модель + локальный booking, затем UI карточек и загрузки, и только после стабилизации — расширение через CRM/доп. фичи.
