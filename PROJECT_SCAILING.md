# PROJECT SCALING: Шаблон "ИИ агент администратор" (amoCRM -> Bitrix24)

## Контекст задачи

Цель: добавить второй продуктовый шаблон агента (кроме текущего QA-консультанта) — **"ИИ администратор"**, который:

- работает в тех же каналах, что и текущий шаблон (Telegram bot/userbot, WhatsApp userbot; в перспективе WhatsApp Business API),
- может выполнять CRM-действия через **function calling**,
- сначала интегрируется с **amoCRM**, затем расширяется на **Bitrix24**.

---

## Что сейчас реально есть в проекте (проверено по коду)

### 1) Архитектура сервисов

Фактически уже развернуты и связаны:

- `frontend` (React/Vite),
- `backend` (FastAPI + Postgres + Qdrant),
- `bot` (отдельный FastAPI+aiogram сервис для Telegram webhook),
- `wa_bridge` (Node/Baileys для WhatsApp userbot),
- инфраструктура в `docker-compose.yml`.

### 2) Модель данных уже подготовлена под шаблоны и каналы

В `Agent` есть:

- `template_type` (qa/function_calling/...),
- `template_config`,
- `primary_provider`.

В `AgentChannelConnection` есть мультиканальная модель (`provider`, `connection_type`, `encrypted_credentials` и т.д.).

### 3) По факту обработка сообщений пока QA-only

Критически важно: несмотря на `template_type`, фактическая генерация ответа сейчас везде идет через **RAG + `generate_answer_with_context`**.

То есть в рантайме нет отдельного исполняемого контура для `function_calling`/CRM.

### 4) WhatsApp Business API подключается только на уровне сохранения канала

В backend есть endpoint подключения `whatsapp_business_api`, валидация токена через Graph API и сохранение credentials.
Но полноценного входящего/исходящего процессинга этого канала как у Telegram/WhatsApp userbot пока нет.

### 5) UI не управляет шаблонами как продуктом

Страница создания агента сейчас в основном про **каналы + системный промпт + документы**.
Явного продуктового выбора шаблона "Консультант / Администратор CRM" в UX еще нет (хотя backend поле есть).

---

## Что в `ARCHITECTURE_DIAGRAM.md` устарело или требует уточнения

Диаграмма полезна как концепт, но сейчас не полностью отражает актуальное состояние:

1. В диаграмме ядро процессинга указано как `bot/core/message_processor.py`.
   - Фактически есть и `backend/app/channels/message_processor.py` (другая реализация).
   - Наблюдается дублирование логики между `bot` и `backend`.

2. В диаграмме заявлен WhatsApp Business API как future.
   - Сейчас уже есть endpoint подключения канала в backend, но нет полнофункционального runtime-контура обработки сообщений.

3. В диаграмме логика выглядит "унифицированной", но в реальности есть несколько точек входа с похожей бизнес-логикой (bot, backend external API, channel managers).

Рекомендация: при реализации CRM-шаблона сначала унифицировать исполнительный слой шаблонов, иначе новые функции придется дублировать в нескольких сервисах.

## Дополнительные фичи для шаблона "ИИ администратор" (целесообразные)

Ниже фичи, которые реально усилят ценность CRM-шаблона и окупятся:

1. **Режим подтверждения действий (Action Confirmation)**
   - Для рискованных операций (смена ответственного, удаление/закрытие, изменение суммы сделки) агент запрашивает подтверждение у пользователя.
   - Снижает риск ошибочных CRM-изменений.

2. **Policy Guardrails по ролям**
   - Настраиваемые правила: какие tool-операции доступны этому агенту и в каком объеме.
   - Пример: "можно создавать лиды и комментарии, но нельзя менять воронку".

3. **Операционный журнал (Audit Trail)**
   - Логировать не только диалог, но и каждое CRM-действие: `tool_name`, аргументы (с маскировкой PII), результат, инициатор, канал.
   - Нужен для поддержки, разбора инцидентов и доверия бизнеса.

4. **Idempotency и защита от дублей**
   - Для create/update операций хранить `idempotency_key`.
   - Особенно важно в мессенджерах при ретраях/повторной доставке.

5. **Сценарий "недостаточно данных"**
   - Если для CRM-операции не хватает обязательных полей, агент не "галлюцинирует", а задает уточняющие вопросы по чек-листу.

6. **Human handoff / оператор**
   - Команда для передачи диалога живому менеджеру + маркировка в аналитике.
   - Для сложных кейсов и высоких чеков критично.

7. **SLA и retry-политика CRM**
   - Таймауты, экспоненциальные ретраи, circuit breaker.
   - Ответ пользователю в стиле: "Запрос принят, операция в обработке".

8. **Мульти-CRM абстракция (amoCRM first, Bitrix24 next)**
   - Сразу строить через adapter-интерфейс, чтобы второй провайдер добавлялся без переписывания бизнес-логики.

## Поэтапный план реализации

Ниже план, разделенный на этапы с целями. Он рассчитан на внедрение без "ломки" текущего QA-потока.

### Этап 0. Архитектурная консолидация (обязательная база)

**Цель этапа:** убрать дублирование процессинга и сделать единый вход для шаблонных стратегий.

Что сделать:

- Ввести единый `TemplateExecutionService` (или `AgentRuntimeService`) в backend.
- Внутри сделать стратегию:
  - `qa` -> текущий RAG flow,
  - `function_calling` (или новый `crm_admin`) -> новый CRM flow.
- Перевести `external/chat` и channel managers на вызов этого слоя.
- В bot-сервисе оставить тонкий transport-adapter без бизнес-логики.

Результат:

- единая точка для всех шаблонов,
- минимизация дублирования,
- проще масштабировать и тестировать.

---

### Этап 1. Продуктовая модель шаблона "ИИ администратор"

**Цель этапа:** формально описать поведение админ-шаблона в данных агента.

Что сделать:

- Определить canonical `template_type`: рекомендую `crm_admin` (чтобы не путать с "техническим" `function_calling`).
- Добавить/зафиксировать структуру `template_config` (JSON):
  - `crm_provider` (`amocrm`/`bitrix24`),
  - `allowed_tools`,
  - `confirmation_policy`,
  - `fallback_mode`,
  - `field_mapping` (опционально).
- Миграция значений и валидация схемы.
- Обновить API схемы и ответы frontend.

Результат:

- шаблон становится не просто строкой, а управляемой конфигурацией.

---

### Этап 2. CRM Adapter Layer (amoCRM first)

**Цель этапа:** подготовить устойчивый слой интеграции с CRM, не завязанный на конкретного провайдера.

Что сделать:

- Ввести интерфейс `CRMProvider` с операциями:
  - `find_contact`, `create_contact`,
  - `find_lead`, `create_lead`, `update_lead`,
  - `add_note`, `create_task`, `assign_owner` (MVP subset).
- Реализовать `AmoCRMProvider`.
- Хранить credential bundle шифрованно (по аналогии с каналами).
- Реализовать health-check + token validation endpoint при подключении CRM.

Результат:

- готовый слой для function calling с amoCRM,
- база для Bitrix24 без рефакторинга ядра.

---

### Этап 3. Tool Registry + Function Calling Runtime

**Цель этапа:** дать LLM управляемый и безопасный доступ к CRM операциям.

Что сделать:

- Реализовать `ToolRegistry` (доступные функции зависят от `template_config.allowed_tools`).
- Поддержать цикл:
  1) LLM предлагает tool call,
  2) backend валидирует аргументы (Pydantic schema per tool),
  3) выполняет CRM action через adapter,
  4) возвращает результат в LLM для финального ответа пользователю.
- Ввести safety:
  - подтверждения для risk-level high,
  - deny-list чувствительных полей,
  - idempotency key.

Результат:

- "ИИ администратор" реально взаимодействует с CRM, а не имитирует это текстом.

---

### Этап 4. Канальная интеграция для CRM-шаблона

**Цель этапа:** обеспечить единое поведение админ-шаблона во всех чат-каналах.

Что сделать:

- Все текущие каналы (telegram bot/userbot, whatsapp userbot) направлять в единый runtime.
- Сохранить контекст пользователя по `user_external_id` + channel.
- Добавить channel-aware normalizer (например, JID в WhatsApp).
- Протоколировать source channel в каждом tool action.

Результат:

- один и тот же CRM-агент ведет себя консистентно в разных мессенджерах.

---

### Этап 5. UI/UX и онбординг нового шаблона

**Цель этапа:** сделать шаблон доступным пользователю как отдельный продуктовый сценарий.

Что сделать:

- На `createAgent` добавить выбор шаблона:
  - "Консультант (RAG)",
  - "Администратор CRM".
- При выборе `crm_admin` показывать блок подключения CRM (amoCRM):
  - домен/endpoint,
  - токен/ключи,
  - тест подключения.
- Экран настройки разрешенных действий (`allowed_tools`) и политики подтверждений.

Результат:

- пользователь настраивает CRM-агента без ручного редактирования JSON/config.

---

### Этап 6. Аналитика, аудит, наблюдаемость

**Цель этапа:** сделать шаблон эксплуатационно надежным.

Что сделать:

- Расширить таблицу аналитики/логов:
  - `tool_name`, `tool_args_hash`, `tool_status`, `latency_ms`, `crm_provider`.
- Метрики:
  - доля успешных tool calls,
  - latency по CRM операциям,
  - частота fallback-to-text,
  - error budget.
- Добавить dashboard секцию "CRM действия агента".

Результат:

- прозрачность работы агента и быстрая диагностика проблем.

---

### Этап 7. Security & Compliance hardening

**Цель этапа:** безопасная эксплуатация CRM-интеграций в production.

Что сделать:

- Маскирование PII в логах.
- Шифрование и ротация CRM credential secret.
- Ограничение tool args (schema + max lengths + allow-list).
- HTTPS enforcement и внутренние подписи для чувствительных endpoint-ов.

Результат:

- снижение рисков утечки/неправомерного изменения CRM данных.

---

### Этап 8. Подключение Bitrix24 (после стабилизации amoCRM)

**Цель этапа:** расширить шаблон до мульти-CRM без изменения UX и core-runtime.

Что сделать:

- Реализовать `Bitrix24Provider`, совместимый с тем же `CRMProvider` интерфейсом.
- Добавить provider-specific field mappings.
- Провести контрактные тесты: один набор кейсов прогоняется для amoCRM и Bitrix24.

Результат:

- подключение второго CRM как расширение, а не новый проект "с нуля".

## MVP-срез (что запускать первым)

Чтобы получить ценность быстро, рекомендую MVP в таком объеме:

1. `crm_admin` шаблон + unified runtime,
2. amoCRM adapter c 4-5 действиями:
   - поиск контакта,
   - создание контакта,
   - создание сделки,
   - добавление заметки,
   - постановка задачи,
3. function calling с обязательной валидацией аргументов,
4. подтверждение рискованных действий,
5. аудит tool calls и базовые метрики.

Это уже даст работающего "ИИ администратора" для большинства операционных сценариев.

---

## Риски и как их снять заранее

1. **Дублирование логики между `bot` и `backend`**
   - Снять на Этапе 0 через единый runtime.

2. **Нестабильность CRM API / лимиты**
   - Retry policy + graceful fallback + очереди для тяжёлых операций.

3. **Галлюцинации LLM в аргументах**
   - Жесткая schema-валидация + ask-back (уточнение данных у пользователя).

4. **Ошибочные массовые изменения CRM**
   - Confirmation policy + role guardrails + idempotency.

---

## Итого

Проект уже имеет хороший фундамент для второго шаблона: мультиканальная модель, analytics, channel connections, шифрование credential данных и готовая инфраструктура.

Главный разрыв сейчас: `template_type` существует в данных, но не в реальном рантайме обработки сообщений.

Правильная стратегия — сначала сделать единый template-runtime и CRM adapter layer, затем включить `crm_admin` через function calling на amoCRM, и только после стабилизации добавлять Bitrix24 как второй адаптер.
